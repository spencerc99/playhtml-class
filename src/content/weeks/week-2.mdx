## How does the web know who's on the bench?

- The internet is a network of computers communicating through a shared set of rules, or protocols. Despite its ethereal reputation, the internet is technically physical. It relies heavily on an underwater and underground telecommunications infrastructure originally laid down in the 20th century, deeply rooted in the geopolitical history of colonialism and the Cold War.

![1901 Eastern Telegraph cables](/images/1901_Eastern_Telegraph_cables.png)
[Eastern Telegraph Company Undersea Cables (1901)](https://commons.wikimedia.org/wiki/File:1901_Eastern_Telegraph_cables.png)

It can be very fragile sometimes (for instance, when an underwater cable is damaged, it can disrupt communication across the globe). When we build real-time digital spaces today, our software code runs directly on top of these historical, physical pathways.

![Shark Eating Undersea Cable](/images/sddefault.jpg)
[Sharks are Attacking the Internet! - Youtube](https://www.youtube.com/watch?v=o0mxdCljXwA)

The web is built on a request-response model, which means that computers (clients) send requests to other computers (servers) and wait for a response. A server is basically a computer that stores and serves content to other computers. When you visit a website, your computer sends a request to the server where the website is hosted, and the server responds by sending back the requested content.

![An image showing a computer that has a sticky note on it that says "this machine is a server, do not power down!!"](/images/do-not-turn-off.jpg)
[This computer is a server. DO NOT SHUT IT DOWN!!](https://blog.perguth.de/posts/2024-12-16-this-computer-is-a-server-do-not-shut-it-down/)

For instance, when we visit a site like [playhtml.fun](https://playhtml.fun), our computer sends a request to the server where the site is hosted, and the server responds by sending back the HTML, CSS, and JavaScript files that make up the site.

## Real-Time Communication & Persistence

This model (called the request-response model) works perfectly for loading static pages, but it has a major limitation for creating communal spaces: the server only knows about you the exact second you ask for something. Once it sends back those files, it completely hangs up and forgets you are there. It has no idea you are still sitting on the website looking at the screen.

To create a shared web experience where you can see other people in real-time, this one-way, request-response model breaks down. If the web only updates when you pull data via a request, how does your browser know when someone else has just sat down on the bench next to you?

To solve this, we have to change to a completely different protocol, Web Sockets, which allows for two-way communication between the client and the server. Instead of making a request and waiting for a response, the client and server can send messages to each other at any time after they perform an initial "handshake". The server can push updates to the client without the client having to ask for them, and the client can send messages to the server without waiting for a response. This allows for real-time communication and collaboration, which is essential for creating spaces on the web that feel inhabited by other people live.

![Web Socket Protocol Diagram](/images/Websocket_connection.png)

And to get your actions to stick around even after you refresh the page, we need to "persist" that state and data somewhere that it can be retrieved, which requires a database. This is a secure location that saves the data and allows you to retrieve it later. These are often relational or key-value stores that allow you to store and retrieve data quickly and efficiently.

Setting up these systems is more complicated than hosting a static website. You cannot just use [GitHub Pages](https://pages.github.com/) or [Netlify](https://www.netlify.com/) to host a Web Socket server, because they are designed for static sites. Instead, you need to use a hosting service that supports Web Sockets, such as [Heroku](https://www.heroku.com/), [AWS](https://aws.amazon.com/), or [DigitalOcean](https://www.digitalocean.com/). You also need to write server-side code to handle the Web Socket connections and manage the state of the communal space.

This is why using a library like playhtml is so helpful. The library hosts the infrastructure for you, so you don't have to worry about setting up your own. It also provides a simple API for managing the state of the communal space and synchronizing it across all connected clients.

Under the hood, playhtml relies on [Cloudflare](https://www.cloudflare.com/), a massive global network infrastructure. Instead of spending weeks configuring backend servers and WebSocket protocols, you just drop a small script into your HTML file. The infrastructure handles the heavy lifting, turning your static webpage into a multiplayer space instantly.

### Can-mirror

The `can-mirror` attribute is the easiest way to make a custom element collaborative, because you don't model any data yourself: it mirrors the element's own state. It automatically syncs every attribute of the original element (position, rotation, scale, color) and the internal state of form elements (text areas, inputs, etc.), so whatever is on your screen shows up on everyone else's.

<CodeDemo demo={<MirrorTextareaDemo />}>

```html
<textarea can-mirror id="text-area" rows="4"></textarea>
```

</CodeDemo>

It also syncs styling. Because `can-mirror` watches every attribute, anything you change on the element — including its inline `style` — shows up for everyone. Here, a button paints a rectangle a random color, and that color follows to every other screen:

<CodeDemo demo={<MirrorColorDemo />}>

```html
<div can-mirror id="color-rect"></div>
<button id="color-btn">random color</button>
```

```javascript
const rectangle = document.getElementById('color-rect');
const button = document.getElementById('color-btn');
button.addEventListener('click', () => {
  // change the style locally; can-mirror syncs it to everyone
  const hue = Math.floor(Math.random() * 360);
  rectangle.style.background = `hsl(${hue}, 80%, 70%)`;
});
```

</CodeDemo>

This can be useful for creating shared text areas, collaborative drawing spaces, or any other element that you want to keep in sync across clients.

const guestbook = document.getElementById('guestbook');

Check out the full playground for can-mirror [here](https://playhtml.fun/docs/advanced/mirror-playground/).

`can-mirror` is the right tool when the DOM _is_ the shared state: whatever's on your screen should be on everyone's screen, with no logic in between. But what if you want to _compute_ something from that shared state (like what % of people did X?)? For that, we model the data ourselves with `can-play`.

### can-play

The `can-play` attribute allows you to define custom data that each element stores and use that data to update how the element behaves and shows up. This is the most customizable and expressive attribute, but it requires you to think about the data you need up front based on how you want someone to interact with it, and then describe how that data turns into what people see.

#### Start simple: a visit counter

We can start with something simple, like a visit counter. Think about the interaction and what is actually changing. For a visit counter, one number changes: the count starts at `0` and goes up as people arrive.

```html
<div can-play id="visit-counter">0</div>
<script>
  // you can also do window.getElementById('visit-counter')
  const visitCounter = document.getElementById('visit-counter');

  // 1. the data this element stores, and what it starts as
  visitCounter.defaultData = { visits: 0 };

  // 2. how that data turns into what people see
  visitCounter.updateElement = ({ element, data }) => {
    element.textContent = data.visits;
  };

  // 3. count this visitor once, when their page loads
  visitCounter.onMount = ({ getData, setData }) => {
    setData((visits) => visits + 1);
  };
</script>
```

`updateElement` runs every time the data changes for everyone on the page, so the number stays in sync for everyone. For a single value like this, hand-writing that one line (`element.textContent = data.visits`) is simple and completely fine.

Now let's make this more complex. A counter tells you _how many_ people showed up, but you don't have any more information about each person. So now let's ask each visitor a question and show their answers.

#### When the UI is a list, or computed from the data

A poll like this is really just the visit counter scaled up: instead of one number, we keep a tally for each option, and we show each option's share of the total as a bar. That small step changes two things:

- the bar widths are **computed** from the votes (each option's share of the total), and
- the options are a **list** that we render, one row each.

```html
<div can-play id="room-poll">
  <button data-id="plants">
    <span class="bar"></span>
    <span class="label">more plants</span>
    <span class="count">0</span>
  </button>
  <button data-id="jukebox">
    <span class="bar"></span>
    <span class="label">a jukebox</span>
    <span class="count">0</span>
  </button>
  <p class="total">0 votes</p>
</div>
<script>
  const poll = document.getElementById('room-poll');

  poll.defaultData = {
    options: [
      { id: 'plants', label: 'more plants', votes: 0 },
      { id: 'jukebox', label: 'a jukebox', votes: 0 },
    ],
  };

  poll.updateElement = ({ element, data }) => {
    const total = data.options.reduce((sum, o) => sum + o.votes, 0);
    data.options.forEach((option) => {
      const row = element.querySelector(`[data-id="${option.id}"]`);
      const percent = total ? (option.votes / total) * 100 : 0;
      row.querySelector('.bar').style.width = percent + '%';
      row.querySelector('.count').textContent = option.votes;
    });
    element.querySelector('.total').textContent = total + ' votes';
  };

  poll.onClick = (event, { setData }) => {
    const row = event.target.closest('[data-id]');
    if (!row) return;
    setData((draft) => {
      draft.options.find((o) => o.id === row.dataset.id).votes += 1;
    });
  };
</script>
```

It works, but the logic starts to get tricky because we have HTML code that defines the start, and separate Javacript code modifying the HTML every time the data changes. It's hard to know what is actually showing up in the DOM from the code itself.

#### The reactive `view` API

There is an alternative API for this case to make this clearer to express, but it will be more complex / new for those used to plain HTML. Instead of _patching_ the DOM step by step, you write one function that describes what the markup _should be_ for any given state, and playhtml re-renders it for you whenever the data changes:

```html
<div can-play id="room-poll"></div>
<script type="module">
  import { html, playhtml, repeat, styleMap } from 'https://unpkg.com/playhtml';

  playhtml.init();

  playhtml.register('room-poll', {
    defaultData: {
      options: [
        { id: 'plants', label: 'more plants', votes: 0 },
        { id: 'jukebox', label: 'a jukebox', votes: 0 },
      ],
    },
    view: ({ data, setData }) => {
      const total = data.options.reduce((sum, o) => sum + o.votes, 0);
      const vote = (id) =>
        setData((draft) => {
          draft.options.find((o) => o.id === id).votes += 1;
        });

      return html`
        ${repeat(
          data.options,
          (option) => option.id,
          (option) => {
            const percent = total ? (option.votes / total) * 100 : 0;
            return html`
              <button @click=${() => vote(option.id)}>
                <span
                  class="bar"
                  style=${styleMap({ width: percent + '%' })}
                ></span>
                <span class="label">${option.label}</span>
                <span class="count">${option.votes}</span>
              </button>
            `;
          },
        )}
        <p>${total} votes</p>
      `;
    },
  });
</script>
```

This may look strange, but it's mostly the same HTML with some new syntax that allows you to interpolate the live data as it is changing. Each time the data changes, we "re-render" this HTML using the new data. We encourage you to try playing around with both! If you are more comfortable the the first version, you can definitely do everything using that API as well, but it might just get a bit confusing.

#### A Guestbook!

Earlier, the `can-mirror` guestbook just copied `<li>` elements between screens. This works but can get confusing as the guestbook logic grows. Here's a more complex example for comparison.

The first thing to figure out is the _shape_ of our data. Unlike the counter's single number, each guestbook entry is an object: the message someone left, when they left it, and an `id` so we can track it as the list changes.

```js
{ id: 'k3f9z', message: 'hi from the bench :)', at: 1719560400000 }
```

The guestbook itself is just a growing list of these. It starts empty (`entries: []`), so we write the shape down as a comment to remember what goes in it:

```html
<div can-play id="guestbook"></div>
<script type="module">
  import { html, playhtml, repeat } from 'https://unpkg.com/playhtml';

  playhtml.init();

  playhtml.register('guestbook', {
    // a growing list of entries, each: { id, message, at }
    defaultData: { entries: [] },
    view: ({ data, setData }) => {
      const sign = (event) => {
        event.preventDefault();
        const input = event.target.querySelector('input');
        const message = input.value.trim();
        if (!message) return;
        setData((draft) => {
          draft.entries.push({
            id: crypto.randomUUID(),
            message,
            at: Date.now(),
          });
        });
        input.value = '';
      };

      return html`
        <p>${data.entries.length} notes left</p>
        <form @submit=${sign}>
          <input placeholder="leave a note..." />
          <button type="submit">sign</button>
        </form>
        <ul>
          ${repeat(
            [...data.entries].reverse(),
            (entry) => entry.id,
            (entry) => html`
              <li>
                ${entry.message}
                <small>${new Date(entry.at).toLocaleTimeString()}</small>
              </li>
            `,
          )}
        </ul>
      `;
    },
  });
</script>
```

#### Which one should I use?

- **`can-mirror`** — the shared thing is literally the DOM (a textarea, a list you append to), with no logic in between.
- **`can-play` with `updateElement`** — you're tracking one or two values and updating them by hand is trivial, like the visit counter.
- **`can-play` with `view`** — the UI is a list, or anything **computed** or **conditional** on shared state. Describe the result once and let it re-render.
