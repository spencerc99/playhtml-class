## Making Public Spaces on the Web

Seating spots along with protected backs provide safety for people to familiarize with a space. It's a balance between openness to other people and still feeling safe to be yourself.

![](https://kaarwan.s3.amazonaws.com/public/blog/media/1/prospectrefuge161jpeg_1773667726227g)
from [kaarwan.com](https://www.kaarwan.com/blog/architecture/prospect-and-refuge-in-architecture-designing-spaces-people-feel-comfortable-in?id=2128)

How does this compare to the web?

1. Most people are **lurkers**. They are peeking out from inside a home where no one can see them. This is different from sitting in a public space, where you are actually showing that you are there. There's a baseline cost for you to show up.
2. When we do show ourselves and post, it's to the entire world—our profiles, content, and entire history visible for all to see.
3. Our choices are binary: completely private and unperceived or completely public and visible to the entire world.

Remember **gradients of intimacy**. How do we let people observe first, then take small actions, so they feel comfortable taking larger ownership of the space?

Not all benches are created equal. We still set the context around the bench and what people can do on it.

Sometimes benches can even be a [guerilla act of resistance](https://sfbabc.org/), providing public seats in a space where no one has before.

And when we open up our own spaces to the public, we take on the responsibility of **hosting**. We have greater control over the space and also the responsibility to steward it. What happens if someone does something we don't like?

We've talked about what makes these spaces feel good, but why are they important?

I think the Internet, at its best, brings us closer to other people and cultures, some of whom we might not have otherwise encountered. Rather than assimilating into a global monoculture, we've seen how the internet can cause an explosion of diversity and creativity. Its promise is that the web can bring us closer to each other, while giving us space to express and celebrate our unique differences.

The pluriverse is a concept popularized by anthropologist Arturo Escobar in [Designs for the Pluriverse: Radical Interdependence, Autonomy, and the Making of Worlds](https://en.wikipedia.org/wiki/Designs_for_the_Pluriverse) which describes "a world in which many worlds fit" to advocate for the co-existence of multiple, potentially conflicting ways of being and organizing society.

That's what I want to see from the internet! Thousands of interfaces and spaces and experiences that are completely different, not feeds under different names.

## Reading & Lecture Discussion (30 mins)

- What are the different kinds of spaces and interactions that are essential to a healthy digital public space? Are there examples you've experienced? Are there examples where it's done the opposite?
- In cities, we have local governments that are responsible for public spaces and are beholden to their constituents to do so. When they don't do their job, we can protest and fight for change. In digital space, it's hard to point to an equivalent. There are the major companies that control the majority of how people browse the web and different international institutions that dictate how the internet works (IETF, W3C, etc.). How do we maintain and ensure public digital space structurally?
- One challenge with digital public space is that different websites are completely separate islands. This models encourages us to create new, siloed experiences rather than say hosting a pop-up in an existing space. As a result, digital public spaces are often very individual. How do we create spaces that are more integrated, connected, and encourage us to contribute back to the community?

## Identity & Permissions

As we grow in data that is being added from various visitors, we need to think about moderation. How do we steward a good space? Ultimately, for the spaces we create, we have the responsibility to take care of them.

While playhtml currently doesn't support secure permissions (because that is very complex!), we can still use some simple workarounds to get access to moderating a space. These are not fully secure to someone deliberately trying to hack it, but they are [secure by obscurity](https://en.wikipedia.org/wiki/Security_through_obscurity), which is often good enough for these small spaces.

We'll be hiding the admin controls using small behavioral gates, kind of like a password!

---

![](https://upload.wikimedia.org/wikipedia/commons/thumb/e/e2/Konami_Code.svg/330px-Konami_Code.svg.png)
[Konami Code](https://en.wikipedia.org/wiki/Konami_Code). We'll borrow this practice of having a secret sequence of keys or codes you enter to unlock the feature.

For example, here's some things we could do:

- `?admin` query param that toggles admin panel
- lock it behind a password field
- hiding it unless you press a combination of key shortcuts
- clicking a transparent button on a particular part of the page

### Soft admin on a guestbook

Same guestbook as last week. Per-row **delete** buttons only appear once admin is unlocked — via `?admin` or `⌘⇧A` / `Ctrl⇧A`.

<CodeDemo demo={<GuestbookAdminDemo />}>

```html
<div can-play id="guestbook"></div>
<script type="module">
  import { html, playhtml, repeat } from 'https://unpkg.com/playhtml';

  const isAdmin = () =>
    new URLSearchParams(location.search).has('admin') ||
    sessionStorage.getItem('admin') === '1';

  const unlock = () => sessionStorage.setItem('admin', '1');

  // Simpler than Konami: Cmd/Ctrl + Shift + A
  window.addEventListener('keydown', (event) => {
    if (
      (event.metaKey || event.ctrlKey) &&
      event.shiftKey &&
      event.key === 'a'
    ) {
      event.preventDefault();
      unlock();
      // toggle .is-admin / re-render so delete buttons show
    }
  });

  playhtml.register('guestbook', {
    defaultData: { entries: [] },
    view: ({ data, setData }) => {
      const admin = isAdmin();

      const sign = (event) => {
        event.preventDefault();
        const input = event.target.querySelector('input');
        const message = input.value.trim();
        if (!message) return;
        setData((draft) => {
          draft.entries.push({
            name: window.cursors?.name || 'someone',
            message,
            at: Date.now(),
          });
        });
        input.value = '';
      };

      const remove = (at) => {
        if (!admin) return;
        setData((draft) => {
          const i = draft.entries.findIndex((e) => e.at === at);
          if (i >= 0) draft.entries.splice(i, 1);
        });
      };

      return html`
        ${admin ? html`<div class="admin-bar">admin unlocked</div>` : null}
        <form @submit=${sign}>
          <input placeholder="leave a note..." />
          <button type="submit">sign</button>
        </form>
        <ul>
          ${repeat(
            [...data.entries].reverse(),
            (entry) => html`
              <li>
                <b>${entry.name}</b>: ${entry.message}
                ${admin
                  ? html`<button type="button" @click=${() => remove(entry.at)}>
                      delete
                    </button>`
                  : null}
              </li>
            `,
          )}
        </ul>
      `;
    },
  });
</script>
```

</CodeDemo>

Try it: add `?admin` to the URL, or press `⌘⇧A` / `Ctrl⇧A`. A delete button shows up on each note.

### Freeze signing behind a password

Same obscurity idea, different shape: a **freeze signing** control is on the page (blurred), and a hardcoded password reveals it. Freezing is shared data on the guestbook — notes stay, but nobody can add new ones until you unfreeze.

<CodeDemo demo={<PasswordLockDemo />}>

```html
<div id="moderation">
  <div class="panel">
    <p>Closed for the night: freeze signing on the guestbook.</p>
    <button type="button" id="toggle-freeze">freeze signing</button>
  </div>
  <form id="gate">
    <input type="password" placeholder="password" />
    <button type="submit">unlock</button>
  </form>
</div>
<script>
  const PASSWORD = 'bench'; // hardcoded on purpose — soft gate only
  const panel = document.getElementById('moderation');

  document.getElementById('gate').addEventListener('submit', (event) => {
    event.preventDefault();
    const value = event.target.querySelector('input').value.trim();
    if (value === PASSWORD) {
      sessionStorage.setItem('unlocked', '1');
      panel.classList.add('is-unlocked'); // CSS drops the blur
    }
  });

  document.getElementById('toggle-freeze').addEventListener('click', () => {
    if (sessionStorage.getItem('unlocked') !== '1') return;
    playhtml.getHandle('guestbook').setData((draft) => {
      draft.frozen = !draft.frozen;
    });
  });
</script>
```

</CodeDemo>

### In the future

This is sufficient for moderation from trusted people, but it's not great for things like wanting to let people be able to change just the things they made or granting more permissions to people who have earned trust.

Real permissioning, tied to each person's unique ID, is on the roadmap which will enable these kinds of things. If you're interested, you can take a look at the WIP work here: https://github.com/spencerc99/playhtml/pull/264

## Connecting the Web

To really make public spaces on the web, we need to connect people across the web, not just within single websites. we were online (WWO) is the next evolution of playhtml. It's a browser extension that brings playhtml to every website you visit to turn the entire internet into a shared space.

https://wewere.online

The benefit to playhtml websites is that people get a stable identitifer that travels with them across different websites, and it opens up the ability for actions on one site to affect another or for people to bring objects from one place to another.

So you can use this to carry the same "identity" across different playhtml websites. For example, this is how I trigger stuff on my website when I'm home: spencer.place

### Shared elements (same domain + cross domain)

[Shared elements](https://playhtml.fun/docs/advanced/shared-elements/) let one page publish a source (`shared`) and other pages — on the **same domain** or another site — subscribe with `data-source="domain/path#elementId"`.

You already use this in class: the Showcase owns `student-projects`, and week pages submit into it via `dataSource`. Each page also has a tiny glowing orb by the title — that's that page's own home beacon.

Live porch lamp on this page (the source). Beside it, a same-page mirror reads the source for teaching — a real consumer on another page/site uses `data-source` (code below).

<CodeDemo demo={<SharedLampSourceDemo />}>

```html
<!-- Source: this page publishes the lamp -->
<div id="porch-lamp" shared can-play>💡</div>
<script>
  const lamp = document.getElementById('porch-lamp');
  lamp.defaultData = { on: false };
  lamp.updateElement = ({ element, data }) => {
    element.classList.toggle('is-on', data.on);
  };
  lamp.onClick = (_e, { data, setData }) => setData({ on: !data.on });
</script>
```

### Webring: is anyone home?

Let's try making an example live webring where each site glows if the host is online.

Each class page publishes its own **shared beacon** (`page-beacon-home`, `page-beacon-week-4`, …) that pulses `lastSeen` while that page is open. The webring below mirrors every class route with `data-source` — glow means someone is on that page right now.

Look at the little orb by this week's title: that's _this_ page's beacon. Open `/` or another week in a second tab and watch that page's dot light up here.

```html
<!-- On each page (unique id per route) -->
<div id="page-beacon-week-4" shared can-play></div>
<script>
  const beacon = document.getElementById('page-beacon-week-4');
  beacon.defaultData = { lastSeen: 0 };
  beacon.onMount = ({ setData }) => {
    const pulse = () =>
      setData((d) => {
        d.lastSeen = Date.now();
      });
    pulse();
    const id = setInterval(pulse, 4000);
    return () => clearInterval(id);
  };
</script>
```
