## Sync and Async

We've been talking about intimacy gradients, and part of what lets you build them is having different modes of interaction for different spaces and contexts. Any space that feels welcoming is successful at facilitating meaningful encounters had many different modes of interaction. It also sets the context appropriately so that you know that you can participate and how to do so.

These are social norms that happen easily in the real world because you can watch what other people do before trying yourself. In a digital space, we have to create space for these norms to be visible, by showing what have done before and setting the stage for what level of interaction is appropriate.

Beyond the design of the interactions, the way you design and cultivate the space also has a big impact on how people treat it. If it looks handmade and has very specific indicators of your personality, people may feel more reverent towards it. If it looks like a corporate website, people will treat it that way, too.

One spectrum I find useful to think about is across a spectrum of **asynchronous** and what is **synchronous**.

**Asynchronous** can happen without everyone being there at the same moment. Think comments on social media, entries in a guestbook, or the art / reviews left on a wall at a cafe. They are lower pressure and can change and accumulate over time, so they give you a sense of what is possible and what has happened before.

**Synchronous** happen with people present spontaneously. Like live cursors on this page, seeing a typing indicator in a message, or helping someone out when they spill their coffee or ask for the wifi password. These are momentary, ephemeral interactions.

These two are very different interactions to design for and they map to two different data models in playhtml. Asynchronous things must be saved somewhere, so you have to think about what _state_ is being saved. That's how you use `defaultData` and the like in `can-play`. Synchronous things aren't meant to be persistent, so there's a separate presence (awareness) API that's used for live things. There's also a way to use _events_, which are live things that aren't data-driven.

We also want to think about individual vs collective contributions, and the level of effort or intentionality required for the interaction.

![](/week-3/social-presence-map.png)

I think any good social space has a mix of these, but you could also choose to focus on one or the other and see how that feels. The low-effort ones are good for socializing norms and getting you to feel safe and comfortable with the space to participate. The higher-effort ones allow for more intimate, meaningful encounters.

### State: a visit counter (async)

To start, we must think about our data. What is the information we must store for the interaction we want to enable?

```javascript
{
  // Required. Starting shared state. Must be an object (or a function that
  // returns one) — not a bare number or string. Synced across the room.
  defaultData: { count: 0 },
  // defaultData: (element) => ({ color: element.dataset.color }),

  /*
    ctx: {
      data,                // shared synced state (read-only snapshot)
      localData,           // per-user, per-tab; not synced
      awareness,           // array of every user's awareness value for this element
      awarenessByStableId, // Map<stableId, awareness value>
      element,             // the HTMLElement

      setData,             // set the shared state
      setLocalData,        // set the local state
      setMyAwareness,      // set your ephemeral awareness value
    }
  */

  // --- update path: provide updateElement OR view, not both ---
  updateElement(ctx) {
    // ctx — see Callback context above. Write the DOM from ctx.data.
    // Do not call ctx.setData here — it loops.
  },
  view(ctx) {
    // ctx — see Callback context above. Return a lit-html template.
    // Mutually exclusive with updateElement, onClick, onDrag, onDragStart.
  },
   // Per-user, per-tab state. Never synced. Drag anchors, drafts, UI flags.
  defaultLocalData: undefined,

  // Your starting awareness value for this element. Ephemeral — clears on disconnect.
  myDefaultAwareness: undefined,
  updateElementAwareness(ctx) {
    // ctx — Callback context + myAwareness
  },

  // --- event handlers (ignored when using view) ---
  onClick(e, ctx) {},       // e: MouseEvent; ctx — Callback context
  onDragStart(e, ctx) {},   // e: MouseEvent | TouchEvent, once at drag start
  onDrag(e, ctx) {},         // e: MouseEvent | TouchEvent, each move until release

  onMount(ctx) {
    // for any additional event listeners or other logic for setting data
    return () => {}; // cleanup on unmount
  },
}
```

The simplest version is a visit counter: one number that starts at `0` and goes up each time someone clicks to say they're here.

<CodeDemo demo={<VisitCounterDemo />}>

```html
<div can-play id="visit-counter">
  <button type="button">I'm here!</button>
  <p><span class="count">0</span> people have checked in</p>
</div>
<script>
  const visitCounter = document.getElementById('visit-counter');

  // 1. the data this element stores, and what it starts as
  visitCounter.defaultData = { count: 0 };

  // 2. how that data turns into what people see
  visitCounter.updateElement = ({ element, data }) => {
    element.querySelector('.count').textContent = data.count;
  };

  // 3. bump the count when someone clicks the button
  visitCounter.onClick = (event, { setData }) => {
    setData((data) => {
      data.count += 1;
    });
  };
</script>
```

</CodeDemo>

`updateElement` runs every time the data changes for anyone on the page, so the number stays in sync for everyone. The value is persisted, so it keeps climbing across refreshes and visits.

### Richer state: who just visited

Visitor count tells you _how many_ people came, but nothing about _who_. So let's try to add some more intentional info, like showing the names of the people who checked in recently.

<CodeDemo demo={<VisitCounterRecentDemo />}>

```html
<div can-play id="visit-log">
  <button type="button">I'm here!</button>
  <p><span class="count">0</span> people have checked in</p>
  <p>recent visitors</p>
  <ul class="recent"></ul>
</div>
<script>
  const visitLog = document.getElementById('visit-log');

  // count is still here; we just also keep the last few visitors
  visitLog.defaultData = { count: 0, recent: [] };

  visitLog.updateElement = ({ element, data }) => {
    element.querySelector('.count').textContent = data.count;
    const list = element.querySelector('.recent');
    // newest first; textContent keeps other people's names as plain text
    list.replaceChildren(
      ...[...data.recent].reverse().map((visit) => {
        const row = document.createElement('li');
        row.textContent = visit.name;
        row.style.color = visit.color;
        return row;
      }),
    );
  };

  visitLog.onClick = (event, { setData }) => {
    setData((data) => {
      data.count += 1;
      data.recent.push({
        name: window.cursors?.name || 'someone',
        color: window.cursors?.color,
        at: Date.now(),
      });
      // keep data small: only remember the last 5
      if (data.recent.length > 5) data.recent.splice(0, data.recent.length - 5);
    });
  };
</script>
```

</CodeDemo>

This still persists and also remembers a little about each person.

### Presence: who's here right now (sync)

Now for ephemeral, shared interactions. This is what the **presence (awareness)** API is for. Instead of `defaultData`, each visitor publishes a `myDefaultAwareness` value, and `updateElementAwareness` gives you access to a live list of everyone's values.

There are three different levels to this:

- Scoped to one element → element myDefaultAwareness
- Page-wide → playhtml.presence.setMyPresence('status', \{ text: 'typing' \})
- Person-specific -> window.cursors

Live cursors, which you see on this site, we mentioned last week are a special case of this because it represents the fundamental identity of each person on the website. We've baked in a few parts of their identity which you can access directly from the `playhtml` object for use. For example, you can get and set the name and the color of the cursor from the `window.cursors` object. These are automatically saved to `localStorage` so they persist across refreshes (but aren't synced).

```html
<script>
  // this only works if you set cursors: true when you init!
  // this is how your profile is set!
  window.cursors.name = 'John Doe';
  window.cursors.color = 'red';

  console.log(window.cursors.name, window.cursors.color);
</script>
```

You can also use this to easily show everyone who is here right now.

### Events: a one-off moment

Sometimes you don't want lasting state _or_ a standing presence list — you just want to mark a moment, once, for whoever's around. That's an **event**. Here we combine the pieces: each visitor's awareness tracks whether they're hovering a zone, and the first time three people hover at once, we `dispatchPlayEvent` so everyone present sees a little celebration. The event leaves nothing behind; it just happens.

<CodeDemo demo={<HoverZoneDemo />}>

```html
<style>
  @keyframes zone-spin {
    to {
      transform: rotate(360deg) scale(3);
    }
  }
  #hover-zone.celebrate {
    animation: zone-spin 0.9s ease-in-out;
  }
</style>
<div can-play id="hover-zone">
  <p>hover here together</p>
  <p><span class="count">0</span>/3 hovering</p>
</div>
<script>
  const zone = document.getElementById('hover-zone');

  // each visitor only tracks their own hover state (presence, not saved)
  zone.defaultData = {};
  zone.myDefaultAwareness = { hovering: false };

  // no saved data to render, but can-play still needs an updateElement
  zone.updateElement = () => {};

  zone.onMount = ({ getElement, setMyAwareness }) => {
    const el = getElement();
    el.addEventListener('mouseenter', () => setMyAwareness({ hovering: true }));
    el.addEventListener('mouseleave', () =>
      setMyAwareness({ hovering: false }),
    );
  };

  let wasBelow = true; // only fire as we *cross* the threshold, not every tick
  zone.updateElementAwareness = ({ element, awareness }) => {
    const hovering = awareness.filter((a) => a?.hovering).length;
    element.querySelector('.count').textContent = hovering;
    if (hovering >= 3 && wasBelow) {
      playhtml.dispatchPlayEvent({ type: 'zone-celebrate' });
    }
    wasBelow = hovering < 3;
  };

  // an event is a one-off broadcast: everyone present runs this once
  playhtml.registerPlayEventListener('zone-celebrate', {
    onEvent: () => {
      zone.classList.add('celebrate');
      zone.addEventListener(
        'animationend',
        () => zone.classList.remove('celebrate'),
        { once: true },
      );
    },
  });
</script>
```

</CodeDemo>

These three properties (state, presence, events) show most of the range of playhtml. Most interactions are just some combination of them.

## Defining your Data

Last week we focused on `can-mirror`, where the DOM _is_ the shared state while **`can-play`** requires you to define the data and how the element should change in response to data changes. When someone's interaction changes the data, playhtml syncs the data and everyone's view updates from it automatically. This gives you full flexibility over the library.

### Working with Lists

One of the most powerful ways to add interesting data interactions involves working with lists of things that grow with how people interact with them!

Say we want to ask each visitor a question and show everyone's answers. A poll like that is really just the visit counter scaled up: instead of one number, we keep a tally for each option, and we show each option's share of the total as a bar. This small change has two big implications:

- the bar widths are **computed** from the votes (each option's share of the total), and
- the options are a **list** that we render, one row each.

<CodeDemo demo={<PollImperativeDemo />}>

```html
<div can-play id="room-poll">
  <button data-id="plants">
    <span class="bar"></span>
    <span class="label">more plants</span>
    <span class="count">0</span>
  </button>
  <button data-id="jukebox">
    <span class="bar"></span>
    <span class="label">a jukebox</span>
    <span class="count">0</span>
  </button>
  <p class="total">0 votes</p>
</div>
<script>
  const poll = document.getElementById('room-poll');

  poll.defaultData = {
    options: [
      { id: 'plants', label: 'more plants', votes: 0 },
      { id: 'jukebox', label: 'a jukebox', votes: 0 },
    ],
  };

  poll.updateElement = ({ element, data }) => {
    const total = data.options.reduce((sum, o) => sum + o.votes, 0);
    data.options.forEach((option) => {
      const row = element.querySelector(`[data-id="${option.id}"]`);
      const percent = total ? (option.votes / total) * 100 : 0;
      row.querySelector('.bar').style.width = percent + '%';
      row.querySelector('.count').textContent = option.votes;
    });
    element.querySelector('.total').textContent = total + ' votes';
  };

  poll.onClick = (event, { setData }) => {
    const row = event.target.closest('[data-id]');
    if (!row) return;
    setData((draft) => {
      draft.options.find((o) => o.id === row.dataset.id).votes += 1;
    });
  };
</script>
```

</CodeDemo>

(Next week we'll show you how to do something based on _your answer_ vs others)

This works, but it starts to get confusing because what you see in the HTML (0 votes) doesn't reflect what is actually going to show. So we have an experimental slightly more complex API that makes this clearer to express.

### The reactive `view` API

Instead of _patching_ the DOM when the data changes via `updateElement`, you write one function that describes what the HTML _should_ be for any given state.

We use `playhtml.register('<ID>', {options})` to register a new element with the given ID. The options object is a configuration object for the element rather than having to put the options on the element itself. The main change is using `view` instead of `updateElement`.

<CodeDemo demo={<PollViewDemo />}>

```html
<div can-play id="room-poll"></div>
<script type="module">
  import { html, playhtml, repeat } from 'https://unpkg.com/playhtml';

  playhtml.register('room-poll', {
    defaultData: {
      options: [
        { id: 'plants', label: 'more plants', votes: 0 },
        { id: 'jukebox', label: 'a jukebox', votes: 0 },
      ],
    },
    view: ({ data, setData }) => {
      const total = data.options.reduce((sum, o) => sum + o.votes, 0);
      const vote = (id) =>
        setData((draft) => {
          draft.options.find((o) => o.id === id).votes += 1;
        });

      return html`
        ${repeat(
          data.options,
          (option) => option.id,
          (option) => {
            const percent = total ? (option.votes / total) * 100 : 0;
            return html`
              <button @click=${() => vote(option.id)}>
                <span class="bar" style="width: ${percent}%"></span>
                <span class="label">${option.label}</span>
                <span class="count">${option.votes}</span>
              </button>
            `;
          },
        )}
        <p>${total} votes</p>
      `;
    },
  });
</script>
```

</CodeDemo>

This may look strange, but it's mostly the same HTML with some new syntax that allows you to interpolate the live data as it is changing. Each time the data changes, we "re-render" this HTML using the new data. We encourage you to try playing around with both! If you are more comfortable with the first version, you can definitely do everything using that API as well, but it might just get a bit confusing.

### A guestbook

Earlier, a `can-mirror` guestbook just copied `<li>` elements between screens. That works for a quick prototype, but gets confusing as the logic grows. With `can-play`, we model the entries as data and render them.

This uses [lit-html](https://lit.dev/), which is a popular library for building custom components using HTML that improves on these things we're talking about. It uses some new syntax like `html` and `repeat` to interpolate (insert dyanmic data) into the HTML.

The first thing to figure out is the _shape_ of our data. Unlike the counter's single number, each guestbook entry is an object: who left it, the message, and when.

```js
{ name: 'Spencer', message: 'hi from the bench :)', at: Date.now() }
```

The guestbook itself is just a growing list of these. It starts empty (`entries: []`), so we write the shape down as a comment to remember what goes in it:

<CodeDemo demo={<GuestbookViewDemo />}>

```html
<div can-play id="guestbook"></div>
<script type="module">
  import { html, playhtml, repeat } from 'https://unpkg.com/playhtml';

  playhtml.register('guestbook', {
    // a growing list of entries, each: { name, message, at }
    defaultData: { entries: [] },
    view: ({ data, setData }) => {
      const sign = (event) => {
        const form = event.target;
        const input = form.querySelector('input');
        const message = input.value.trim();
        if (!message) return;
        setData((draft) => {
          draft.entries.push({
            name: window.cursors?.name || 'someone',
            message,
            at: Date.now(),
          });
        });
        input.value = '';
      };

      return html`
        <p>${data.entries.length} notes left</p>
        <form @submit=${sign}>
          <input placeholder="leave a note..." />
          <button type="submit">sign</button>
        </form>
        <ul>
          ${repeat(
            [...data.entries].reverse(),
            (entry) => html`
              <li>
                <b>${entry.name}</b>: ${entry.message}
                <small>${new Date(entry.at).toLocaleTimeString()}</small>
              </li>
            `,
          )}
        </ul>
      `;
    },
  });
</script>
```

</CodeDemo>

Because the entries are persisted, the guestbook fills up over time instead of resetting on refresh.

## Recap

**Which tag should I use?**

- **`can-mirror`** — the shared thing is literally the DOM (a textarea, a list you append to), with no logic in between.
- **`can-play` with `updateElement`** — you're tracking one or two values and updating them by hand is trivial, like the visit counter.
- **`can-play` with `view`** — the UI is a list, or anything **computed** or **conditional** on shared state. Describe the result once and let it re-render.

**Which API should I use?**

- **data**: state that should be persisted over time
- **awareness/presence** - state that should show live but not be persisted
- **events** - things that should happen just once for everyone but not be persisted or represented as data.
