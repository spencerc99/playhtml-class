## Sync and Async

We've been talking about intimacy gradients, and part of what lets you build them is having different modes of interaction for different spaces and contexts. Any space that feels welcoming is successful at facilitating meaningful encounters had many different modes of interaction. It also sets the context appropriately so that you know that you can participate and how to do so.

These are social norms that happen easily in the real world because you can watch what other people do before trying yourself. In a digital space, we have to create space for these norms to be visible, by showing what have done before and setting the stage for what level of interaction is appropriate.

Beyond the design of the interactions, the way you design and cultivate the space also has a big impact on how people treat it. If it looks handmade and has very specific indicators of your personality, people may feel more reverent towards it. If it looks like a corporate website, people will treat it that way, too.

One spectrum I find useful to think about is across a spectrum of **asynchronous** and what is **synchronous**.

**Asynchronous** can happen without everyone being there at the same moment. Think comments on social media, entries in a guestbook, or the art / reviews left on a wall at a cafe. They are lower pressure and can change and accumulate over time, so they give you a sense of what is possible and what has happened before.

**Synchronous** happen with people present spontaneously. Like live cursors on this page, seeing a typing indicator in a message, or helping someone out when they spill their coffee or ask for the wifi password. These are momentary, ephemeral interactions.

These two are very different interactions to design for and they map to two different data models in playhtml. Asynchronous things must be saved somewhere, so you have to think about what _state_ is being saved. That's how you use `defaultData` and the like in `can-play`. Synchronous things aren't meant to be persistent, so there's a separate presence (awareness) API that's used for live things. There's also a way to use _events_, which are live things that aren't data-driven.

## Live Code

To make this concrete, let's take one interaction and walk it along the spectrum: start with something that persists, make it live, then fire a one-off moment.

### State: a visit counter (async)

The async end is **state**: data that playhtml saves and syncs for you. `can-play` is how you define it — you give an element some `defaultData`, then describe how that data turns into what people see. The simplest version is a visit counter: one number that starts at `0` and goes up as people arrive.

<CodeDemo demo={<VisitCounterDemo />}>

```html
<div can-play id="visit-counter">0</div>
<script>
  const visitCounter = document.getElementById('visit-counter');

  // 1. the data this element stores, and what it starts as
  visitCounter.defaultData = { visits: 0 };

  // 2. how that data turns into what people see
  visitCounter.updateElement = ({ element, data }) => {
    element.textContent = data.visits;
  };

  // 3. bump the count by one every time the page loads
  visitCounter.onMount = ({ setData }) => {
    setData((data) => {
      data.visits += 1;
    });
  };
</script>
```

</CodeDemo>

`updateElement` runs every time the data changes for anyone on the page, so the number stays in sync for everyone. The value is persisted, so it keeps climbing across refreshes and visits — that's the async half of the spectrum.

### Richer state: who just visited

A bare count tells you _how many_ people came, but nothing about _who_. Because it's just state, we can store more: alongside the count, keep a short list of recent visitors — each with their name, color, and when they stopped by. Same model, slightly bigger shape.

<CodeDemo demo={<VisitCounterRecentDemo />}>

```html
<div can-play id="visit-log">
  <div class="big"><span class="count">0</span> visits</div>
  <p>recent visitors</p>
  <ul class="recent"></ul>
</div>
<script>
  const visitLog = document.getElementById('visit-log');

  // count is still here; we just also keep the last few visitors
  visitLog.defaultData = { count: 0, recent: [] };

  visitLog.updateElement = ({ element, data }) => {
    element.querySelector('.count').textContent = data.count;
    const list = element.querySelector('.recent');
    // newest first; textContent keeps other people's names as plain text
    list.replaceChildren(
      ...[...data.recent].reverse().map((visit) => {
        const row = document.createElement('li');
        row.textContent = visit.name;
        row.style.color = visit.color;
        return row;
      }),
    );
  };

  visitLog.onMount = ({ setData }) => {
    setData((data) => {
      data.count += 1;
      data.recent.push({
        name: window.cursors?.name || 'someone',
        color: window.cursors?.color,
        at: Date.now(),
      });
      // keep defaultData small: only remember the last 5
      if (data.recent.length > 5) data.recent.splice(0, data.recent.length - 5);
    });
  };
</script>
```

</CodeDemo>

It still survives a refresh, and now it remembers a little about each person. This is the same async idea, just with a richer shape — exactly the kind of thing we'll lean on for guestbooks and notes below.

### Presence: who's here right now (sync)

Now the sync end. "Who's here _right now_" shouldn't persist — when you leave, you should disappear. That's what the **presence (awareness)** API is for. Instead of `defaultData`, each visitor publishes a `myDefaultAwareness` value, and `updateElementAwareness` hands you the live list of everyone's values. Nothing is saved; refresh and the list rebuilds from whoever is actually connected.

<CodeDemo demo={<PresenceCountDemo />}>

```html
<div can-play id="who-is-here">
  <p><span class="count">0</span> here right now</p>
  <ul class="people"></ul>
</div>
<script>
  const here = document.getElementById('who-is-here');

  // presence is per-visitor and not saved, so it lives in awareness, not data
  here.defaultData = {};
  here.myDefaultAwareness = {
    name: window.cursors?.name || 'someone',
    color: window.cursors?.color,
  };

  // there's no saved data to render, but can-play still needs an updateElement
  here.updateElement = () => {};

  // awareness is the live array of everyone's values (including yours)
  here.updateElementAwareness = ({ element, awareness }) => {
    element.querySelector('.count').textContent = awareness.length;
    element.querySelector('.people').replaceChildren(
      ...awareness.map((person) => {
        const chip = document.createElement('li');
        chip.textContent = person.name;
        chip.style.color = person.color;
        return chip;
      }),
    );
  };
</script>
```

</CodeDemo>

Open this page in a second tab to watch the count climb — and close it to watch yourself disappear. That's the sync half: live, but with nothing left behind.

### Events: a one-off moment

Sometimes you don't want lasting state _or_ a standing presence list — you just want to mark a moment, once, for whoever's around. That's an **event**. Here we combine the pieces: each visitor's awareness tracks whether they're hovering a zone, and the first time five people hover at once, we `dispatchPlayEvent` so everyone present sees a little celebration. The event leaves nothing behind; it just happens.

<CodeDemo demo={<HoverZoneDemo />}>

```html
<div can-play id="hover-zone">
  <p>hover here together</p>
  <p><span class="count">0</span>/5 hovering</p>
</div>
<script>
  const zone = document.getElementById('hover-zone');

  // each visitor only tracks their own hover state (presence, not saved)
  zone.defaultData = {};
  zone.myDefaultAwareness = { hovering: false };

  // no saved data to render, but can-play still needs an updateElement
  zone.updateElement = () => {};

  zone.onMount = ({ getElement, setMyAwareness }) => {
    const el = getElement();
    el.addEventListener('mouseenter', () => setMyAwareness({ hovering: true }));
    el.addEventListener('mouseleave', () =>
      setMyAwareness({ hovering: false }),
    );
  };

  let wasBelow = true; // only fire as we *cross* the threshold, not every tick
  zone.updateElementAwareness = ({ element, awareness }) => {
    const hovering = awareness.filter((a) => a?.hovering).length;
    element.querySelector('.count').textContent = hovering;
    if (hovering >= 2 && wasBelow) {
      playhtml.dispatchPlayEvent({ type: 'zone-celebrate' });
    }
    wasBelow = hovering < 2;
  };

  // an event is a one-off broadcast: everyone present runs this once
  playhtml.registerPlayEventListener('zone-celebrate', {
    onEvent: () => {
      // TODO: your little celebration animation here
    },
  });
</script>
```

</CodeDemo>

These three — **state**, **presence**, and **events** — are the whole toolkit. Most interactions are just some combination of them. The rest of today digs into the state side, since that's where guestbooks and notes live.

## Defining your Data

Last week we focused on `can-mirror`, where the DOM _is_ the shared state. **`can-play`** flips that: you define **data** for each element, and write code that turns that data into what people see. When someone's interaction changes the data, playhtml syncs the data — and everyone's view updates from it.

That's exactly what the visit counter above did: `defaultData` held the count, `updateElement` turned it into text, and `onMount` bumped it. `can-play` is the most customizable and expressive option, but it asks you to think about the data you need up front — based on how you want someone to interact with it — and then describe how that data turns into what people see. For a single value, hand-writing that one line (`element.textContent = data.visits`) is simple and completely fine. The interesting part is what happens when the data grows.

### When the UI is a list, or computed from the data

Say we want to ask each visitor a question and show everyone's answers. A poll like that is really just the visit counter scaled up: instead of one number, we keep a tally for each option, and we show each option's share of the total as a bar. That small step changes two things:

- the bar widths are **computed** from the votes (each option's share of the total), and
- the options are a **list** that we render, one row each.

<CodeDemo demo={<PollImperativeDemo />}>

```html
<div can-play id="room-poll">
  <button data-id="plants">
    <span class="bar"></span>
    <span class="label">more plants</span>
    <span class="count">0</span>
  </button>
  <button data-id="jukebox">
    <span class="bar"></span>
    <span class="label">a jukebox</span>
    <span class="count">0</span>
  </button>
  <p class="total">0 votes</p>
</div>
<script>
  const poll = document.getElementById('room-poll');

  poll.defaultData = {
    options: [
      { id: 'plants', label: 'more plants', votes: 0 },
      { id: 'jukebox', label: 'a jukebox', votes: 0 },
    ],
  };

  poll.updateElement = ({ element, data }) => {
    const total = data.options.reduce((sum, o) => sum + o.votes, 0);
    data.options.forEach((option) => {
      const row = element.querySelector(`[data-id="${option.id}"]`);
      const percent = total ? (option.votes / total) * 100 : 0;
      row.querySelector('.bar').style.width = percent + '%';
      row.querySelector('.count').textContent = option.votes;
    });
    element.querySelector('.total').textContent = total + ' votes';
  };

  poll.onClick = (event, { setData }) => {
    const row = event.target.closest('[data-id]');
    if (!row) return;
    setData((draft) => {
      draft.options.find((o) => o.id === row.dataset.id).votes += 1;
    });
  };
</script>
```

</CodeDemo>

It works, but the logic starts to get tricky because we have HTML code that defines the start, and separate Javascript code modifying the HTML every time the data changes. It's hard to know what is actually showing up in the DOM from the code itself.

### The reactive `view` API

There is an alternative API for this case to make this clearer to express, but it will be more complex / new for those used to plain HTML. Instead of _patching_ the DOM step by step, you write one function that describes what the markup _should be_ for any given state, and playhtml re-renders it for you whenever the data changes:

<CodeDemo demo={<PollViewDemo />}>

```html
<div can-play id="room-poll"></div>
<script type="module">
  import { html, playhtml, repeat, styleMap } from 'https://unpkg.com/playhtml';

  playhtml.init();

  playhtml.register('room-poll', {
    defaultData: {
      options: [
        { id: 'plants', label: 'more plants', votes: 0 },
        { id: 'jukebox', label: 'a jukebox', votes: 0 },
      ],
    },
    view: ({ data, setData }) => {
      const total = data.options.reduce((sum, o) => sum + o.votes, 0);
      const vote = (id) =>
        setData((draft) => {
          draft.options.find((o) => o.id === id).votes += 1;
        });

      return html`
        ${repeat(
          data.options,
          (option) => option.id,
          (option) => {
            const percent = total ? (option.votes / total) * 100 : 0;
            return html`
              <button @click=${() => vote(option.id)}>
                <span
                  class="bar"
                  style=${styleMap({ width: percent + '%' })}
                ></span>
                <span class="label">${option.label}</span>
                <span class="count">${option.votes}</span>
              </button>
            `;
          },
        )}
        <p>${total} votes</p>
      `;
    },
  });
</script>
```

</CodeDemo>

This may look strange, but it's mostly the same HTML with some new syntax that allows you to interpolate the live data as it is changing. Each time the data changes, we "re-render" this HTML using the new data. We encourage you to try playing around with both! If you are more comfortable with the first version, you can definitely do everything using that API as well, but it might just get a bit confusing.

### A guestbook

Earlier, a `can-mirror` guestbook just copied `<li>` elements between screens. That works for a quick prototype, but gets confusing as the logic grows. With `can-play`, we model the entries as data and render them.

The first thing to figure out is the _shape_ of our data. Unlike the counter's single number, each guestbook entry is an object: the message someone left, when they left it, and an `id` so we can track it as the list changes.

```js
{ id: 'k3f9z', message: 'hi from the bench :)', at: 1719560400000 }
```

The guestbook itself is just a growing list of these. It starts empty (`entries: []`), so we write the shape down as a comment to remember what goes in it:

<CodeDemo demo={<GuestbookViewDemo />}>

```html
<div can-play id="guestbook"></div>
<script type="module">
  import { html, playhtml, repeat } from 'https://unpkg.com/playhtml';

  playhtml.init();

  playhtml.register('guestbook', {
    // a growing list of entries, each: { id, message, at }
    defaultData: { entries: [] },
    view: ({ data, setData }) => {
      const sign = (event) => {
        event.preventDefault();
        const input = event.target.querySelector('input');
        const message = input.value.trim();
        if (!message) return;
        setData((draft) => {
          draft.entries.push({
            id: crypto.randomUUID(),
            message,
            at: Date.now(),
          });
        });
        input.value = '';
      };

      return html`
        <p>${data.entries.length} notes left</p>
        <form @submit=${sign}>
          <input placeholder="leave a note..." />
          <button type="submit">sign</button>
        </form>
        <ul>
          ${repeat(
            [...data.entries].reverse(),
            (entry) => entry.id,
            (entry) => html`
              <li>
                ${entry.message}
                <small>${new Date(entry.at).toLocaleTimeString()}</small>
              </li>
            `,
          )}
        </ul>
      `;
    },
  });
</script>
```

</CodeDemo>

Because the entries are persisted, the guestbook fills up over time instead of resetting on refresh.

### Which one should I use?

- **`can-mirror`** — the shared thing is literally the DOM (a textarea, a list you append to), with no logic in between.
- **`can-play` with `updateElement`** — you're tracking one or two values and updating them by hand is trivial, like the visit counter.
- **`can-play` with `view`** — the UI is a list, or anything **computed** or **conditional** on shared state. Describe the result once and let it re-render.
